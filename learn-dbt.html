What is dbt?

The Git for SQL - version control, tests, and documentation for the queries that power your dashboards.

The 30-second answer

dbt (data build tool) is the standard for transforming data inside your warehouse. You write transformations as SQL files, dbt figures out the dependencies, runs them in the right order, tests the output, and generates living documentation - all with version control built in.

Said differently: dbt is what made "your data team's code" look as professional as "your engineering team's code."

What does dbt actually solve?

Three problems hit every data team eventually:

  1. No version control on SQL. Someone rewrites a metric, breaks three dashboards, no one can roll back.
  2. No tests. A column starts returning nulls. No one notices for two weeks.
  3. No documentation. "What does this column mean?" The answer lives in someone's head.

dbt solves all three with one pattern: SQL files in Git, tested on every change, documented automatically.

The four building blocks

  1. Models. SELECT statements that become tables or views in your warehouse. Each model is one file.
  2. Tests. Assertions about your data - "this column is never null", "this is unique", "values match this list". Run on every model.
  3. Sources. Pointers to raw tables (from Fivetran, Airbyte, etc.). Lets you reference them safely and document them.
  4. Refs. How models depend on other models. dbt builds the dependency graph and runs everything in the right order.

How a dbt project is organized

  1. Sources. Raw tables from outside, declared but not modified.
  2. Staging. One staging model per source table. Renames columns, casts types, light cleanup.
  3. Intermediate. Joins and reshapes that aren't yet business-facing.
  4. Marts. Clean, business-friendly tables organized by domain - finance.revenue, marketing.sessions.

Common pitfalls

  • Skipping tests. "We'll add them later" - you won't. Add them as you build.
  • Going macro-heavy too early. dbt has powerful Jinja macros, but they make debugging hard. Stay simple until duplication actually hurts.
  • Big tables, no incremental. Rebuilding a 500M-row model every hour will burn your warehouse bill. Incremental materializations exist for this.
  • No CI. Run dbt build on every PR. Catch breaks before they merge.

What good looks like

  • Every model has at least one test (usually not_null and unique on the primary key).
  • A clear convention: staging, intermediate, marts.
  • Auto-generated docs site, hosted on your subdomain.
  • A lineage graph you can click through to see "what depends on this column?"
  • Incremental models for any table over ~100M rows.
  • A metrics layer - "revenue" defined once, used everywhere.
